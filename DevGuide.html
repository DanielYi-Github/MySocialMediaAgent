01  核心問題

四大失敗模式

AI 協作開發加速了軟體熵增速度。在享受生產力紅利之前，必須先認識並針對性地解決這四個根本問題。

01
🎯

Agent 沒做你要的

最常見的失敗模式是「失準」。你以為 AI 懂你，但看到產出才發現根本南轅北轍。這是人機之間溝通落差的必然結果。

解法
/grill-with-docs /grill-me
02
💬

Agent 說了太多廢話

AI 被丟進專案後會自己摸索術語。結果是用 20 個字解釋本來 1 個字就能說清楚的概念，浪費 token 也浪費時間。

解法
CONTEXT.md 共用語言
03
🔴

程式碼根本跑不動

對齊問題解決了，但程式還是爛的？這時要看的是回饋迴路。缺乏靜態型別、瀏覽器存取與自動化測試，Agent 就是在盲飛。

解法
/tdd /diagnose
04
🏚️

建出一顆泥球

AI 加速撰碼也同步加速軟體腐化。模組邊界模糊、相依纏繞，最終演變成讓人不敢碰的「泥球」架構。

解法
/improve-codebase-architecture
02  開發流程

從需求到交付

每次功能開發都走完整個循環——不跳過、不敷衍。以下是每個階段的核心活動與對應 Skill。

Phase 0  ·  一次性初始化

專案設定

在每個 repo 執行一次。設定 issue tracker（GitHub / Linear / 本地檔案）、triage label 語彙、文件存放路徑，讓其他所有 Skills 能正常運作。

/setup-matt-pocock-skills
Phase 1  ·  每次功能開始前

Grilling 對齊會議

在動手寫任何一行程式之前，讓 Agent 對你的計畫「進行質詢」。它會沿著決策樹的每個分支深入追問， 對照既有的 CONTEXT.md 挑戰你的用語， 確保你們對「要做什麼」達到真正的共識。每次都用，不例外。

/grill-with-docs 更新 CONTEXT.md 新增 ADR（必要時）
Phase 2  ·  規格化

產出 PRD 與 Issues

將對話脈絡轉為正式 PRD 並提交為 GitHub issue；再把 PRD 拆解為可獨立執行的垂直切片 issues， 每張 issue 都能被任何人或任何 Agent 獨立拿起來做。

/to-prd /to-issues /triage
Phase 3  ·  迭代建構

TDD 紅綠重構循環

一次一個垂直切片，先寫失敗的測試（紅燈），再讓測試通過（綠燈），最後重構讓設計更乾淨（藍燈）。 這個回饋迴路是讓 Agent 產出高品質程式碼的關鍵。

/tdd 靜態型別檢查 自動化測試
Phase 4  ·  問題排查

系統化診斷

遇到頑固 bug 或效能退化時，走完整的診斷迴路：重現 → 最小化 → 提假說 → 加儀器 → 修復 → 加回歸測試。 不憑直覺亂猜，用方法論找根因。

/diagnose /zoom-out
Phase 5  ·  每幾天一次

架構健檢

AI 開發會加速架構腐化，需要定期主動投資設計。搜尋「深化機會」——找出能以更簡單介面封裝更多功能的模組， 並依照 CONTEXT.md 的領域語言重新整理邊界。

/improve-codebase-architecture /zoom-out
Phase 6  ·  上下文切換時

交接文件

將當前對話壓縮成交接文件，讓另一個 Agent（或未來的自己）能無縫接手繼續工作，不需要重建所有上下文。

/handoff

04  TDD 實踐

紅綠重構循環

自動化測試的紅綠重構迴路是確保 Agent 產出品質的核心機制。沒有回饋迴路，Agent 就是在盲飛。

RED
Step 1
寫失敗的測試
定義期望行為
→
GREEN
Step 2
讓測試通過
最小可行實作
→
REFACTOR
Step 3
重構改善設計
測試仍需通過
→
NEXT
Repeat
下一個切片
垂直堆疊進度
「永遠走小步、刻意前進。回饋速率就是你的速度上限。永遠不要承擔超出能力的任務。」
— David Thomas & Andrew Hunt, The Pragmatic Programmer
✂️

垂直切片，而非水平分層

每個 issue 代表一個從 UI 到資料庫的完整功能切片，而不是「先做所有的 model」或「再做所有的 controller」。每個切片都能獨立測試、獨立交付。

🔬

測試要說故事，不要測實作細節

好測試描述的是行為，不是內部實作。測試應該在你重構程式碼後仍然有效，而不是因為你改了一個私有方法名稱就爆炸。

🔁

回饋迴路越短越好

靜態型別、lint、單元測試、整合測試——每一層都是給 Agent 的即時信號。迴路越緊密，Agent 犯錯就越快被抓到，修正成本越低。

05  文件架構

建立共用語言

CONTEXT.md 是整個方法論最強大的工具之一。它讓 Agent 使用與你相同的語言， 讓變數、函數、檔案命名保持一致，並大幅降低每次對話的 token 消耗。

📁 /
  ├── CONTEXT.md     ← 專案領域語彙表，最重要的文件
  ├── CLAUDE.md      ← Agent 行為規則與慣例
  ├── docs/

何時才需要寫 ADR？

三個條件同時成立才需要，缺一不可：

條件一

難以逆轉

改變這個決定的代價是顯著的。若改起來很簡單，就不需要記錄。

條件二

脫離脈絡會讓人困惑

未來的讀者看到這段程式碼會疑惑「為什麼這樣做？」——有必要留下解釋。

條件三

真正的取捨

存在過真正的替代方案，且你因為特定理由選擇了這條路，而非別無選擇。

06  工程哲學

回到根本

這套 Skills 的底層，是幾十年軟體工程積累下來的基本功。AI 時代不廢棄這些原則，反而讓它們比以往更重要。

🗣️

共用語言（Ubiquitous Language）

領域專家和開發者之間的語言鴻溝是軟體複雜度的根源。CONTEXT.md 強制建立唯一的、被所有人（包含 AI）共同使用的術語集，讓對話、程式碼、文件三者一致。

🏗️

深度模組（Deep Modules）

最好的模組是「深的」——以簡單的介面隱藏大量的功能複雜度。與其有很多小而淺的函數互相纏繞，不如讓邊界更少、更深、更穩定。

📅

每天投資設計

Kent Beck 說：「每天投資系統設計。」AI 開發讓這句話更加緊迫——功能可以在幾小時內堆積如山，架構腐化的速度也以相同倍率加快。不主動維護，就等著收拾殘局。

🎯

小步前進，保持掌控

Pragmatic Programmer 強調：回饋速率就是速度上限。一次做一個垂直切片、一次走一個 TDD 循環，讓你始終清楚程式碼處於什麼狀態，而不是等到最後才發現一切都錯了。

🔓

Skills 而非流程框架

GSD、BMAD、Spec-Kit 等框架試圖接管整個開發流程，但這樣會讓流程本身的 bug 變得難以修復。這套 Skills 刻意設計為小型、可獨立使用的工具，保留你的掌控權，讓你 hack 它、修改它、讓它成為你自己的。

「軟體工程的基本功在 AI 時代比以往任何時候都更加重要。這些 Skills 是我盡力將這些基本功凝縮成可重複實踐方法的最佳嘗試。」
— Matt Pocock, mattpocock/skills README
